# Architecture (rendering engine)

## Custom `om://` MapLibre protocol

The app registers a custom protocol with MapLibre in `src/routes/+page.svelte` (`maplibregl.addProtocol('om', ...)`) wired to `omProtocol` from `@openmeteo/weather-map-layer`. Just before, it calls `maplibregl.setWorkerUrl()` with the worker imported via Vite's `?worker&url` query: MapLibre 6 is ESM-only and cannot locate its worker inside a bundler on its own (« Worker failed to load », no tiles). All sources use `om://<https-url-with-query-params>` URLs. Source URLs are constructed in `src/lib/url.ts → getOMUrl()`, which encodes the domain, model run, valid time, variable, vector toggles, tile size, dark mode, and stable hashes of clipping/color settings.

The dev/preview server in `vite.config.ts` injects `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp` headers — they enable `SharedArrayBuffer` for `@openmeteo/file-reader` (zero-copy sharing with tile workers). SAB is an optimisation, not a requirement: `fileReaderConfig.useSAB` comes from `canUseSharedArrayBuffer()` (`src/lib/shared-array-buffer.ts`), which returns false when the page isn't cross-origin isolated (Android WebView exposes the constructor but is never isolated) → plain `ArrayBuffer`s structured-cloned to workers. Never hard-code `useSAB: true` (which is excluded from Vite's `optimizeDeps` along with `@openmeteo/file-format-wasm`).

## Cache de blocs OMfile (`generational-block-cache.ts`)

Le reader partagé (`fileReaderConfig.cache`, `stores/om-protocol-settings.ts`) utilise `GenerationalBlockCache`, une implémentation maison de l'interface `BlockCache` de `@openmeteo/file-reader`, **et non** `BrowserBlockCache`. **Bug corrigé** : l'éviction de `BrowserBlockCache` (0.0.20) relance un `cache.keys()` plus un `match()` par entrée après **chaque** `put`. Ce coût croît avec le cache, et Chrome refuse `keys()` au-delà d'une dizaine de milliers d'entrées (« Operation too large », seuil qui dépend de la longueur des URLs). Vers 1 Go de blocs de 64 Ko, l'éviction échouait à chaque écriture et saturait le backend du Cache API : un `match()` prenait plusieurs secondes et la carte ne chargeait plus.

Le cache écrit dans des **générations** `om-blocks-<n>`. Un compteur `{ current, bytes, entries }` en `localStorage` (`om-blocks:state`) déclenche la rotation à `maxBytes / generations` octets **ou** `MAX_ENTRIES_PER_GENERATION` (4000) entrées. Quatre générations sont conservées ; l'éviction se fait par `caches.delete()` de la plus ancienne. **Aucune opération ne dépend du nombre d'entrées** : ne jamais réintroduire de `Cache.keys()`. Les lectures passent par `caches.match()` (toutes générations). La rotation est sérialisée entre onglets via Web Locks. Une `QuotaExceededError` libère la plus ancienne génération. Un état perdu fait repartir sur une génération neuve, les anciennes restant lisibles. À l'initialisation, l'ancien cache `open-meteo-maps-cache-v1` est supprimé (`LEGACY_CACHE_NAMES`), ce qui débloque les navigateurs déjà touchés. Tests : `tests/generational-block-cache.test.ts` (faux `CacheStorage`).

## SlotManager (double-buffered tiles)

`src/lib/slot-manager.ts` implements an A/B slot system used by `src/lib/layers.ts`. MapLibre's `setUrl`/`setTiles` does not reliably abort in-flight requests, so each data update creates a new source+layers in the pending slot, waits for `source.loaded()`, then cross-fades opacity and removes the old slot after `removeDelayMs`. When changing rendering code, preserve this pattern — there are now four managers (plus one per composition overlay, see below): `rasterManager` (couche raster principale), `rasterManager2` (overlay raster secondaire optionnel, conditionné par `layer2Enabled`), `vectorManager` (contours/grille/étiquettes **et** flèches en mode « selon la variable affichée ») et `arrowManager` (flèches de l'**overlay vent**, sur un niveau de vent dédié). Tous sont créés dans `createManagers()` et doivent être mis à jour via `update()`/`setBeforeLayer()`, jamais en mutant sources/layers directement.

**Reprise sur erreur / blocage (`retry`, `OM_SLOT_RETRY`).** Tous les managers OMfile (principaux, couche 2, superpositions) passent `retry: OM_SLOT_RETRY` (2 rechargements, délai 1 s × n, `stallMs` 20 s). Si la source du slot en attente émet une erreur, ou n'a pas fini de charger au bout de `stallMs`, le slot est rechargé sur la **même URL** (retirer/recréer la source annule les requêtes en vol ; les blocs déjà lus restent dans le cache du reader). Une erreur « fichier absent » (404, `File not found`) n'est pas réessayée : c'est une variable que le domaine ne publie pas, et la réessayer retarderait le commit groupé. Au dernier essai, il n'y a plus de minuterie de blocage, pour ne pas abandonner un chargement lent qui progresse ; une erreur appelle alors `onError`. **Bug corrigé** : sans ça, une seule lecture `.om` en échec (5xx au-delà des 3 essais du reader) ou bloquée (corps de réponse qui n'arrive jamais : le timeout de `fetchRetry` ne couvre que les en-têtes) laissait le raster invisible, ou le spinner tourner sans fin dans le groupe de commit, jusqu'au prochain `update()`. Les utilisateurs devaient changer d'échéance pour voir la carte. Tests : `tests/slot-manager-error.test.ts`.

**Calque « valeurs aux points de grille » (façon Météociel).** Le `vectorManager` porte aussi `vectorGridValuesLayer` (`layers.ts`), un layer `symbol` sur la source-layer `'grid'` qui affiche la valeur **exacte au nœud** (`properties.value`, déjà émise par le package, non interpolée). Le format dépend de la variable : `buildGridValueLabelExprFor`, dans l'unité d'affichage, donne un **entier** pour toutes les variables (`buildGridValueLabelExpr`), **sauf** les précipitations (`precipitation`, `rain`, `showers`, `precipitation_sum`, `isPrecipitationVariable`) : au dixième avec une virgule sous 10 mm (« 0,4 »), en entier au-delà, et en pouces 2 décimales sous 1 in. Pour ces variables, `buildGridValueVisibilityFilter` masque ce qui s'afficherait « 0,0 » (zones sèches). Le calque est gaté par le store persisté `gridValues` (`stores/vector.ts`), **orthogonal** au toggle `vectorOptions.grid` (points orange) ; les deux togglent sous la même section « Grille » (`grid-settings.svelte`). Comme la source-layer `'grid'` n'existe dans les tuiles que si l'URL porte `&grid=true`, `getOMUrlFor` force ce flag dès que **l'un OU l'autre** est actif (`vectorOverride?.grid ?? (vectorOptions.grid || get(gridValues))`) ; un `vectorOverride` explicite (p. ex. `getWindOverlayUrl()` qui passe `grid: false`) reste prioritaire.

**Densité.** Décimation **2D** sur l'`id` GLOBAL stable émis par le fork (`GridPoint.globalIndex`, `id = j·nx + i`, voir la section « Spécificités du fork » du README) : `buildGridDecimationFilter` (`vector-styles.ts`) garde le sous-réseau fixe `i % sx == 0 && j % sy == 0`. `sx` et `sy` visent un espacement écran d'environ `GRID_VALUE_TARGET_PX` (48 px), calculé du pas de grille, avec correction mercator en Y. Le filtre est un `['step', ['zoom'], …]` à paliers entiers. Il est combiné à **`text-allow-overlap: true`** (pas de collision MapLibre) : les étiquettes sont épinglées aux nœuds, un pan ne fait que les translater, sans recalcul. Espacement minimal garanti : `target / 1,5` ≈ 32 px, pire cas d'arrondi du stride. Une étiquette de 4 caractères (≈ 28 px) ne peut donc pas chevaucher sa voisine ; l'invariant est verrouillé en test. **Limite** : sur les grilles gaussiennes (pas d'`id = j·nx + i` exploitable), on se rabat sur une décimation 1D `id % sx`, qui ne décime pas les rangées : l'espacement vertical n'y est pas garanti. **Piège MapLibre** : `['zoom']` n'est accepté qu'en entrée d'un `step` de premier niveau. Un filtre additionnel (visibilité des précipitations) s'applique donc **dans chaque branche** du `step` (`combineGridValueFilters`), jamais en enveloppant la décimation dans un `all`. **Historique** : avant l'`id` global du fork, le package ré-indexait les points par sous-grille rognée (`nxClip` variable avec le viewport), et un décodage `floor(id/grid.nx)` produisait une seule bande horizontale de valeurs sur les domaines monde. Ne jamais décoder `(i, j)` sans l'`id` global. La couche est reconstruite par `reloadVectorStyle()` (changement de domaine ou d'unité). Les contrats runtime (MapLibre accepte `step(zoom)` + `['id']` en filtre ; `number-format` avec `locale: 'fr'`) sont verrouillés par `featureFilter` et `createExpression` (`tests/vector-styles.test.ts`).

**Découplage flèches/contours (overlay vent).** Le `vectorManager` est toujours alimenté par `getOMUrl()` (variable affichée) : ses contours/étiquettes suivent donc la variable affichée. Quand l'overlay vent est actif (`windOverlayEnabled`), `getWindOverlayUrl()` fournit une URL **flèches-seules** (`getOMUrlFor(..., { contours: false, grid: false })`) qui alimente l'`arrowManager` ; sinon l'`arrowManager` est `destroy()`é et d'éventuelles flèches passent par le `vectorManager`. Les deux couches de flèches (`vectorArrowLayer(false)` sur le vectorManager, `vectorArrowLayer(true)` sur l'arrowManager) se gardent mutuellement via `arrowsOnOverlay !== forOverlay` (avec `arrowsOnOverlay = resolveWindArrowLevel() !== null`) pour ne jamais dessiner les flèches en double. **Piège historique** : avant ce découplage, l'overlay basculait toute la source vecteur sur `wind_u_component`, ce qui générait des contours/étiquettes parasites du vent (valeurs en m/s) par-dessus la carte dès que les contours étaient activés. `arrowManager` est mis à jour **avant** `vectorManager` pour que les flèches restent sous les contours/étiquettes (z-order). **Conséquence pour le popup** : `popup.ts` lit la vitesse du vent (mode calque) depuis l'`arrowManager` (`getActiveSourceUrl()`), **pas** le vectorManager — sinon il lirait la valeur de la variable affichée (p. ex. la température) et l'afficherait comme du vent.

**3ᵉ cas — fallback « selon la variable affichée ».** Une seule fonction décide quel niveau l'`arrowManager` rend : `resolveWindArrowLevel()` (`url.ts`). En mode « selon la variable affichée » (`windOverlayEnabled = false`), si la variable affichée n'est **pas** du vent (`isWindVariable`, `vector-styles.ts`), elle dérive un niveau via `deriveDisplayedWindLevel()` (niveau de pression de la variable si le vent y est publié, sinon `10m`) et l'`arrowManager` rend ce vent — sans quoi une `temperature_2m` n'affichait aucune flèche. Le garde de couche (`vectorArrowLayer`) **et** le popup (`popup.ts`) raisonnent désormais sur `resolveWindArrowLevel() !== null` (plus seulement sur `windOverlayEnabled`), si bien que le survol affiche le vent même en mode fallback. La règle « exactement un manager dessine les flèches » est préservée.

**Étiquettes d'isolignes converties dans l'unité d'affichage.** `buildContourLabelExpr(variable, baseUnit, units)` (`vector-styles.ts`) convertit la valeur brute des tuiles (unité de l'échelle de couleurs : `m/s`, `gpm`, `°C`…) vers l'unité choisie via une transformation **affine** (offset + facteur) dérivée de `convertValue` et exprimée en MapLibre (`number-format`). La couleur/largeur restent pilotées par la valeur brute (`modulo`), donc les lignes ne bougent pas. Le `baseUnit` est résolu dans le `layerFactory` via `getColorScale(variable, …).unit`. **Réactivité** : chaque changement d'unité (`unit-settings.svelte`) appelle `reloadVectorStyle()` pour reconstruire les étiquettes — sans ça, seul le géopotentiel se rafraîchissait et le vent restait figé en m/s.

Les managers utilisent un commit **opt-in différé** (`deferCommit: true`) : au lieu de chaque couche faisant un fondu indépendant dès que `source.loaded()`, un coordinateur module-level (`commit-group.ts`, wrappers dans `layers.ts`) — `beginCommitGroup`/`addToCommitGroup`/`tryFlushGroup`/`dropFromGroup` — groupe les managers mis à jour dans le même tick pour qu'ils effectuent leur fondu **ensemble**. `loading` est désactivé et `refreshPopup()` s'exécute une seule fois quand tout le groupe est prêt (ou quand les membres en erreur sont retirés via `dropFromGroup`). `addToCommitGroup` fusionne un manager dans le groupe en vol (utilisé par `reloadVectorStyle`) plutôt que d'écraser le groupe, ce qui évite de bloquer des managers raster déjà en attente.

Le style des contours et des flèches n'est plus codé en dur : il est défini dans `src/lib/vector-styles.ts` (builders data-driven) alimentés par les stores persistés `contourStyle`/`arrowStyle` (`src/lib/stores/vector-styles.ts`), éditables dans le drawer réglages. `reloadVectorStyle()` reconstruit les couches vectorielles en place après une modification de style (tuiles en cache → coût réseau quasi nul).

**Superpositions de composition (`overlay-stack.ts`).** Les sources du store `overlays` (`stores/composition.ts`) sont rendues par une `OverlayStack` : **un `SlotManager` par couche** (`clearOnError`, `deferCommit`, préfixe de source unique `omOverlaySource_<n>` tiré d'un compteur module — jamais réutilisé, sinon le `removeSlot` différé d'un manager détruit purgerait la source du nouveau). Le plan est pur : `desiredOverlayLayers(overlays, ctx, getOverlayOmUrl)` saute les sources indisponibles (`isSourceAvailable`) et celles neutralisées par le fond (`effectiveOverlayFlags`), et produit au plus un plan `raster` (aplat, opacité × `source.opacity`, inséré avant la couche-repère invisible `omOverlayRasterAnchor` — voir plus bas) et un plan `vector` (flèches puis isolignes + étiquettes, avant l'ancrage vecteur) par source, clé `` `${index}:${variable}:${kind}` ``. `planOverlayUpdates` ne recharge que les clés dont la **signature de rendu** change (`overlayRenderSignature` : l'URL, plus l'opacité pour l'aplat ou l'épaisseur pour le vecteur quand elles diffèrent du défaut) ; `sync` rafraîchit toujours `entry.plan` des clés conservées. `getOverlayOmUrl` (`url.ts`) : sans grille, isolignes à `contourInterval` ou sur les paliers (`intervals: 'breakpoints'` → aucun `&intervals=`), `undefined` sur `ANOMALY_DOMAIN`. Les couches réutilisent les builders de `layers.ts` (`rasterLayer`, `arrowLayer`, `vectorContourLayer`/`vectorContourLabelsLayer` paramétrés), injectés via le hook `layers` pour éviter un cycle d'imports. `sync(plans)` détruit les clés retirées et **renvoie** `{ manager, url }[]` sans lancer d'`update()` : `addOmFileLayers` (qui recrée la pile) et `changeOMfileURL` les ajoutent au groupe **après** les managers principaux, appellent `beginCommitGroup`, puis `update('om://' + url)`. **Exception** : si `changeOMfileURL` ne recharge que des superpositions (ni primaire ni couche 2), elles sont **fusionnées** dans le groupe en vol (`addToCommitGroup`) au lieu de l'écraser — sinon un chargement principal en attente ne serait jamais committé. Dans l'autre sens, un rechargement primaire/couche 2 appelle `beginCommitGroup(group, keep)` avec `keep = overlayStack.owns` : les superpositions encore en vol non rechargées par cet appel sont **reportées** dans le nouveau groupe (sinon leur commit différé serait perdu). Sans superposition, rien n'est reporté (comportement historique). Erreur (404) → `dropFromGroup`, couche effacée, pas de toast. Tout manager détruit (`sync` qui retire une clé, `destroyAll`) passe par le hook `onDestroy` → `commitGroup.forget(mgr)` : un manager détruit n'est jamais prêt ni en erreur et bloquerait sinon le flush du groupe (spinner figé, commits différés jamais exécutés). Le coordinateur vit dans `commit-group.ts` (`CommitGroup` : `begin(managers, keep?)`/`tryFlush`/`add`/`drop`/`forget`, testé sans carte) ; `layers.ts` garde des wrappers du même nom. **Z-order des aplats** : `BEFORE_LAYER_RASTER_SECONDARY === BEFORE_LAYER_VECTOR`, donc s'y ancrer ferait recouvrir isolignes/flèches/étiquettes selon l'ordre d'insertion. `addOmFileLayers` pose donc (après chaque `setStyle`, avant toute couche vecteur OMfile) une couche-repère `background` invisible `omOverlayRasterAnchor` sous les départements (ou sous l'ancre vecteur) via `ensureAnchorLayer` ; les aplats de superposition s'insèrent avant elle → sous toutes les couches vecteur, au-dessus de l'aplat principal, et dans l'ordre de la liste : quand un aplat se recharge seul (bascule, opacité, retour après indisponibilité), `planOverlayUpdates` recharge aussi, dans l'ordre, les aplats actifs qui le suivent. `rasterManager2` garde son ancrage historique. `reloadVectorStyle` recharge aussi les managers vecteur des superpositions. `lineWidth` multiplie l'épaisseur des isolignes **et** des flèches (comme upstream) ; `inlineVectors` est ignoré en v1. Sans superposition, le plan est vide : URL, couches et commit strictement inchangés. `+page.svelte` appelle `changeOMfileURL()` quand `overlays` change (le second appel après une action ne recharge rien : plan identique, groupe vide).

`changeOMfileURL()` ne recharge le **primaire** (raster + vecteur) que si `getOMUrl()` diffère de `currentOmUrl` ; la **couche 2** a sa propre déduplication (`currentOmUrl2 !== omUrl2`) et se rafraîchit indépendamment, même quand le primaire n'a pas bougé (changement de variable/activation de l'overlay). Pour forcer un rechargement primaire, invalider `currentOmUrl` (le mettre à `''`) ou changer un paramètre qui alimente `getOMUrl()`.

## Compositions (fond + superpositions)

Portage des « Combined charts » d'open-meteo/maps (#361), en **modèle additif** : le **fond** reste la variable principale (`variable`), rendue par le pipeline historique (`rasterManager`, `vectorManager`, overlay vent, couche 2) ; les **superpositions** (store `overlays`, `ChartSource[]`) s'y **ajoutent** via l'`OverlayStack` (`overlay-stack.ts`, détail de rendu, signatures et z-order dans « Superpositions de composition » ci-dessus ; coordinateur de commit dans `commit-group.ts`). Aucune superposition = aucun changement (URL, couches, popup, commit). Logique pure dans `composition.ts` (`splitChartSources`, `matchPresetComposition`, `effectiveOverlayFlags`, `isSourceAvailable`), presets dans `chart-presets.ts`, (dé)sérialisation dans `chart-encoding.ts`.

**Règles de neutralisation** (`effectiveOverlayFlags`, jamais de doublon avec le fond) : un aplat (`raster`) sur la variable du fond est ignoré ; des isolignes sur la variable du fond sont ignorées si le fond dessine déjà ses contours (`primaryContours`) ; des flèches sont ignorées si elles seraient déjà dessinées par l'`arrowManager` (variable du fond, ou `wind_u_component_<niveau>` du niveau résolu par `resolveWindArrowLevel()`, quand `primaryArrows`) ou si la variable n'a pas de direction (`variableHasDirections`). Une source dont la variable n'existe pas dans le modèle courant (`isSourceAvailable`) n'est pas rendue et apparaît grisée dans l'UI ; elle réapparaît au retour sur un modèle qui la publie. `getOverlayOmUrl` renvoie `undefined` sur `ANOMALY_DOMAIN`.

**Paramètre d'URL `overlays`** : même grammaire que `sources` (`variable[:drapeaux]`, ex. `overlays=geopotential_height_500hPa:c12.5`), omis quand la liste est vide. `urlParamsToPreferences()` le parse (valeur invalide → toast, ignorée ; absent sur un lien explicite `domain`/`variable`, ou vide → superpositions vidées, voir `.claude/rules/stores.md`) ; `updateUrl` l'écrit via `serializeSources`. Le fond voyage dans le paramètre `variable` habituel.

**Infobulle (`popup.ts`)** — portage d'open-meteo/maps (#373, #361). Sous la pastille de valeur, une ligne par superposition (`getOverlayValueSources()` de `layers.ts` → `OverlayStack.activeSources()`, une URL affichée par superposition, aplat préféré au vecteur, dans l'ordre de la liste ; la variable du fond est exclue) : libellé court (`shortLabel`, `popup-format.ts` : « Z 500 », « Pmer », « T 850 »), pression/géopotentiel en plus petit, valeur nulle atténuée ; la tige s'allonge de la hauteur des lignes. Une frame pas encore décodée omet sa ligne au lieu d'afficher une erreur. Un jeton `popupUpdateSeq` empêche une lecture lente d'écraser une position plus récente. **Flèche de direction** dans la pastille : devant la valeur principale si la variable affichée porte une direction (`getValueFromLatLong(...).direction`), sinon devant le vent de l'`arrowManager` (elle remplace alors le séparateur « · ») ; orientée à l'écran via la projection (`screenAngle` : orientation, inclinaison et perspective comprises, réalignée sur `move`), longueur/opacité/épaisseur tirées de la rampe du style des flèches (`arrowStyle`, ramenée dans une plage lisible), interpolée frame par frame en redessinant le tracé SVG (pas de transformation CSS, qui pixelisait). Fonctions pures testées : `tests/popup-format.test.ts`.

**Hors périmètre v1** : `inlineVectors` (ignoré : les flèches/isolignes d'une superposition restent au-dessus de tous les aplats), l'`opacity` de la source de fond d'un preset (non appliquée : le fond passe par le pipeline principal et son opacité globale), superpositions sur `ANOMALY_DOMAIN`, synchronisation des compositions enregistrées entre appareils (localStorage seul).

## Couches Weather AI (cyclones, expérimental)

`src/lib/weather-ai/` rend les cartes expérimentales du modèle IA **WeatherNext Cyclones Mini** servies par l'API du portail (`getWeatherAiApiUrl()`, `runtime-env.ts`, défaut `https://portail.chom.engineering/api/weather-ai`, GET seulement). Contrats de référence : `infoclimat-labs/weather-ai` (`docs/front-carto-integration.md`, `docs/front-mentions-obligatoires.md`, schémas `carto-grid-product`, `cyclone-tracks-product`, `cyclone-cones-public-product`). Ce pipeline est **indépendant** de `om://` : documents JSON d'une autre API, run et échéances propres, pas de SlotManager. Modules : **Périmètre (revue UI/UX de Pam)** : maps ne rend que des **superpositions** — cyclones déclarés, trajectoires, zones à surveiller, cônes — activables sur n'importe quel fond. Les **champs continus** (pression au niveau de la mer, probabilité d'existence cyclonique, température à 2 m, vent à 10 m et précipitations — ces deux derniers seulement dans les runs publiés à trois couches maps, weather-ai#318) ne sont **pas** des superpositions : ce sont les variables du **pseudo-domaine** `weather_ai_wnc_mini` du sélecteur de modèles (voie B : `.om` publiés par le producteur weather-ai au layout `data_spatial/…`, cf. § _Pseudo-domaines_). L'onglet Cyclones IA y renvoie dès l'enregistrement du domaine, que le catalogue du portail ait répondu ou non. Leurs produits du portail restent connus (`PRODUCT_SPECS`) mais ne sont ni proposés ni chargés ; `grid.ts`/`render.ts` et leurs tests (validation, géométrie) sont conservés. **Échéance** : pas de curseur propre, elle suit la **frise principale** (store `time`) via `frame.ts`.

- `api.ts` — types des réponses, `getJson` (toute réponse non `ok` lève `WeatherAiHttpError` ; le 404 arrive en `problem+json`), URLs (`valid_time` encodé).
- `products.ts` — `PRODUCT_SPECS` : produits que le front **sait afficher**, par `product_id` (schéma, variable et unité attendus). Ce n'est pas la liste des couches : le menu vient du catalogue (`discoverProducts` déduplique les entrées produit × échéance), un `product_id` inconnu est ignoré proprement. Quand le portail servira `products[].presentation`, le menu et la légende devront en venir.
- `loader.ts` — `prepareRun` charge **hors écran** un run complet (catalogue, `init_time` via `GET /runs` sur le couple `run_id`/`snapshot_id`, à défaut le produit trajectoires — jamais extrait du `run_id`), valide chaque frame (même `run_id`/`snapshot_id`, `experimental: true`, schéma, géométrie, unité ; probabilité dans [0, 1]) ; une frame ou timeline d'un autre run lève `RunChangedError` (catalogue basculé pendant la séquence → on recommence une fois). Cache `<run_id>:<product_id>:<valid_time>` (`pruneCache` à la bascule). `extendRun` charge après coup une couche activée, pour le **même** run ; le contrôleur réconcilie juste après chaque bascule les couches activées pendant la préparation (`tests/weather-ai-controller.test.ts`).
- `controller.ts` — `useWeatherAi()` (compteur d'utilisateurs : onglet monté ou couche active) : relit le catalogue toutes les 5 min, `AbortController` par chargement, **bascule atomique** (`weatherAiRun` remplacé d'un bloc, jamais complété avec un autre run ; toute erreur garde le run affiché). Ne charge que les trajectoires (légères) ; les grilles (~1-1,5 Mo de JSON par frame) ne sont jamais demandées tant qu'aucun champ continu n'est proposé.
- `grid.ts` — **non rendu aujourd'hui, conservé pour le futur pseudo-domaine** (validation et géométrie des grilles `carto-grid-product`) : `normalizeGrid` : géométrie lue dans `grid`, colonnes 0..359 remises en −180..180, lignes sud → nord ; `sampleGrid` (bilinéaire, bouclage à l'antiméridien) ; `renderMercatorRgba` rasterise **par latitude Mercator, nord en haut** (MapLibre interpole une source `image` dans l'espace Mercator) ; `isolines` : marching squares avec colonne de raccord, une isobare qui franchit ±180 s'arrête sur le méridien des deux côtés sans traverser la carte.
- `tracks.ts` — `classifyTrack` (`ecmwf-tf:<année>:<id>` / `atcf:<id>` = cyclone déclaré, `cyclogenesis_<n>` = **candidat**, affiché seulement comme « Zone à surveiller » en pointillés + halo, jamais coloré par le vent ; autre format = écarté), `buildTracks` regroupe par **`(member, model_track_id)`**, `unwrapLongitudes` déroule les longitudes (−180..180 dans ce produit) pour qu'une piste qui franchit l'antiméridien reste continue. Seul le membre 0 est tracé.
- `cones.ts` — cônes publics servis par le portail (chom-poc-data#260), **flag** `getWeatherAiConesMode()` (`VITE_WEATHER_AI_CONES` / `WEATHER_AI_CONES` : `on` **défaut** depuis la décision de Pam du 23/10/2026, `off` = interrupteur de retrait qui **gagne partout**, y compris contre `?weather_ai_cones=fixture`, `fixture`) : document unique par run, **pas** la boucle par frame. **Découverte** : champ `cones` du catalogue (frère de `produits`, `ConesCatalogEntry` dans `api.ts`, `null` tant que le run servi n'a pas de cônes validés), lu par `discoverProducts` (`products.ts`) seulement si son `run_id` et son `snapshot_id` sont ceux des autres produits ; une entrée cônes dans `produits` est ignorée. Le run découvert porte `validTime` (amorce) et `sha256` du document. **Même run** : le catalogue relu peut annoncer les cônes après coup (job `cone-members` fini après le catalogue du run), les remplacer ou les retirer — `withCatalogCones` (`loader.ts`) met à jour l'entrée sans recharger les autres produits, et `syncCones` (`controller.ts`) relit le document quand le `sha256` change (`weatherAiCones.sha256`) ; ce `sha256` entre dans la signature du plan et la portée du cache géométrique (`map-layers.ts`, `PlanInput.conesId`), sans quoi un document remplacé dans le même run garderait l'ancienne géométrie. **Chargement** : `loadConesDocument` lit `GET /products/global-cyclone-cones-public/data?valid_time=<amorce>` (`null` sans entrée au catalogue ou sur 404 — cônes retirés entre-temps —, toute autre erreur est levée), puis le contrôleur le passe à `validateCones` (même `run_id` **et** `snapshot_id` que le run affiché) ; `cones: null` ne propose rien et n'affiche aucune erreur, les trajectoires restent seules. **Cônes du run précédent (décision de Pam du 26/10/2026)** : le catalogue bascule sur un nouveau run ~1 h avant la fin du job `cone-members`, et le portail ne sert les cônes que du run en ligne (`_cones_du_run`, chom-poc-data `scripts/serving_weather_ai.py`) — un chargement à froid ne peut donc pas les obtenir. Le contrôleur garde en **mémoire de session** (`lastCones`) les derniers cônes validés ; à la bascule (`commitRun`), `keepPreviousCones` (`cones.ts`) les conserve dans `weatherAiCones.previous` seulement s'ils sont du run affiché juste avant, que le catalogue du nouveau run annonce **explicitement** l'attente des siens (`cones: null` → `LoadedRun.conesAwaited` ; un champ absent est un **retrait**, pas une attente), que l'amorce du nouveau run est postérieure de ≤ 12 h (`PREVIOUS_CONES_MAX_AGE_MS`), et que `validateCones` passe encore contre **leur** run. Ils restent pendant les relevés du même run (`withCatalogCones`), y compris si les cônes du run courant sont refusés ou en erreur, et disparaissent dès que ceux du run courant sont validés par `syncCones`, ou au **retrait** (relevé du même run sans champ `cones` ni entrée). `lastCones` est **invalidée** à chaque bascule qui ne les garde pas (retour vers un run plus ancien, run mémorisé qui n'est pas le précédent immédiat), à chaque retrait, et quand l'entrée du run mémorisé est retirée ou remplacée : des cônes retirés ne ressurgissent jamais. **Mentions liées au slot affiché** : `DisplayedState.cones` (`displayed.ts`, `displayedCones` = mêmes conditions que `preparePlan`) porte le document (calibration) et, le cas échéant, `previous` des cônes **réellement montrés** ; il ne change qu'au résultat `shown` du commutateur. Carte flottante, onglet, `weather-ai-mentions.svelte` et infobulle lisent ces métadonnées, jamais `weatherAiCones` ni le catalogue (`DisplayedState.cones.credits` : attribution et licence des cônes affichés, lues au commit ; la section cônes de l'onglet et sa bascule restent tant que des cônes sont affichés, même retirés du catalogue ; l'infobulle compte les échéances des cônes depuis l'`init_time` de leur document et celles des trajectoires depuis `DisplayedState.initTime`, jamais depuis le run sélectionné) : tant que le slot B charge, ou après un délai dépassé, les cônes A restent présentés avec leur calibration et la mention du run précédent. Rendu distinct (`RenderPlan.previousCones` : remplissage atténué, contour en pointillés ; signature et portée de cache propres), mention `previousConesNotice` (« Cônes du run JJ/MM HHZ : ceux du run affiché sont en cours de calcul. ») sur la carte flottante, dans l'onglet et dans `weather-ai-mentions.svelte`, avec la mention de calibration et le `calibration_status` de leur run ; infobulle des centres comptée depuis leur amorce. Les trajectoires restent celles du run courant ; `conesOffered(run, cones)` propose la couche tant que ces cônes sont gardés. Tests : `tests/weather-ai-previous-cones.test.ts`. `fixture` = **démonstration hors API** : `demo.ts → loadDemoRun()` remplace l'appel au catalogue par le run de référence bundlé — trajectoires réelles archivées `fixtures/tracks-reference.fixture.json` (run 18/10/2026 00Z, blocs `tracker`/`sources` retirés) et cônes fictifs du **même** run `fixtures/cones-public.fixture.json` (conformes au schéma, centrés sur les positions réelles, rayons inventés) ; `LoadedRun.demo` affiche un bandeau « Démonstration hors API ». Activable aussi par `?weather_ai_cones=fixture` (le paramètre d'URL ne peut demander que la démo, jamais `on`, et jamais contre `off`) ; fixtures en import dynamique, hors bundle principal). `validateCones` vérifie d'abord les types du document lu sur le réseau (`invalidShape` : nombres finis, rayons > 0, hémisphère et raison d'indisponibilité connus — l'infobulle HTML de `map-layers.ts` n'interpole que ces champs, nombres passés par `int()`), puis refuse tout document dont la `mention` n'est pas exactement `CONES_MENTION`, dont le `calibration_status` est absent ou diffère de celui du catalogue (affiché tel quel à côté de la mention, panneau et carte flottante), dont une raison d'indisponibilité n'est pas une propriété propre de `CONE_REASON_LABELS` (`isConeReason` : ni `toString` ni `__proto__`), d'un autre run, sans `public_delivery_allowed`, ou qui annonce un cône disponible au-delà de la limite du cyclone (`stormLeadLimit` : `maximum_lead_hours` global et du cyclone, et `southern_maximum_lead_hours` dans l'hémisphère sud) ; le rendu (`conesToGeoJson`) applique aussi cette limite. Enveloppe = union des cercles successifs reliés par leurs tangentes (`convex` de chaque paire + `union` turf, rayons km → degrés selon la latitude), coupée à chaque `available: false`.
- `render.ts` — `formatUtc`/`formatLead` ; palette de probabilité et isobares GeoJSON conservées (non rendues) pour le futur pseudo-domaine.
- `frame.ts` — `resolveFrame(times, time)` : échéance Weather AI pour l'heure de la frise = la **plus proche inférieure ou égale** (`exact` / `between`), **rien hors horizon** (`before`/`after` : avant +6 h ou après +72 h, pas de position de +72 h montrée pour une heure à +96 h). Dérivées dans `stores/weather-ai.ts` : `weatherAiFrame`, `weatherAiTime`. La légende (`cardSummary`) annonce « entre deux échéances » / « hors horizon (+6 h à +72 h, …) » et le **run Weather AI** (jamais confondu avec le run du fond).
- `map-layers.ts` + `layer-switcher.ts` + `render-cache.ts` — `syncWeatherAiLayers()` affiche l'état (run × échéance × couches × cônes × thème) **d'un bloc** : `preparePlan` prépare hors écran tout le contenu (trajectoires, cônes), puis `createLayerSwitcher` (même principe que `slot-manager.ts`) le monte dans un **slot neuf** (`weatherAi_<partie>_s<n>`, sources `image`/`geojson` + couches à opacité 0), attend que **toutes** ses sources soient chargées (`isSourceLoaded`), rend le slot visible et retire l'ancien **dans le même tick**. Jamais de mise à jour en place d'une source affichée : on ne voit donc jamais les isobares d'un état avec l'image ou les trajectoires d'un autre. Un commit dépassé par un plus récent est abandonné à toute étape (préparation ou chargement) ; une signature identique à l'état affiché ne recommute pas. **Délai dépassé** (15 s sans chargement complet, résultat `timeout`) : le slot incomplet est retiré (sources, écouteurs, minuterie) et l'état précédent **reste affiché** — jamais d'affichage incomplet ; `syncWeatherAiLayers` passe `weatherAiStatus` en erreur (`RENDER_TIMEOUT_MESSAGE`, effacé au prochain affichage réussi) et réessaie au relevé suivant (`CATALOG_POLL_MS`). Les rendus sont mémoïsés par `RunScopedCache`, clé `<run_id>:<product_id>:<valid_time>`, avec une génération par run : un rendu qui se termine après une bascule de run est **refusé et libéré** (`dispose`). Couches posées au-dessus de toutes les autres ; un `setStyle` (`reloadStyles()`, `map-controls.ts`) purge les slots, l'adaptateur le détecte (`exists`) et recommute. Infobulle au survol des couches du slot affiché (`.weather-ai-tooltip`, `styles.css`). Tests sans carte : `tests/weather-ai-switcher.test.ts` (courses, ordre de commutation, re-style, délai).

**CORS** : le portail renvoie `Access-Control-Allow-Origin: *` sur `/api/weather-ai/*`, erreurs comprises, depuis le 18/10/2026 (chom-poc-data#258) ; l'app l'appelle donc en direct, sous COEP `require-corp`, sans en-tête CORP. Un échec réseau (`TypeError`) s'affiche « API Weather AI injoignable (réseau ou CORS) » et garde le run affiché. Le proxy `'/api/weather-ai'` du dev/preview server (`vite.config.ts`, `VITE_WEATHER_AI_API_URL=/api/weather-ai`) reste disponible pour diagnostiquer, sans effet en prod.

**Mentions** (obligatoires, `weather-ai-panel.svelte` + `weather-ai-map-card.svelte`) : badge Expérimental et avertissement « ne remplace aucune alerte » visibles en permanence dès qu'une couche est active, échéance relative + `valid_time` UTC + `run_id` sur la carte, échéance écoulée signalée, attribution et `license_notice` reçues telles quelles, non-responsabilité ECMWF non reformulée, « not an officially supported Google product », DOI Copernicus ; mention de calibration des cônes à chaque affichage de cônes.

## GeoJSON overlays (départements)

`src/lib/departments-layer.ts` (contours des départements français) suit ce pattern : une source `geojson` dédiée (`omDepartmentsSource`) + un layer `line` (`omDepartmentsLayer`) placé sous `BEFORE_LAYER_VECTOR`, togglé par le store persisté `showDepartments`. Il expose `buildDepartmentsLineLayer(isDark, visible)` (builder pur du `LineLayerSpecification`, testé sans carte ; couleur figée selon `basemapTheme`), `ensureDepartmentsLayer()` (ajoute source vide + layer une fois, idempotent) et `refreshDepartments(visible = get(showDepartments))` (bascule la `visibility` via `setLayoutProperty` ; au 1er affichage, fetch **paresseux** du GeoJSON puis `setData`, données ensuite cachées en portée module — pas de re-fetch). **Piège re-style** : `setStyle` (donc `reloadStyles()`) purge sources/layers custom → `refreshDepartments()` est rappelé après chaque re-style (`map-controls.ts`) pour recréer source+layer (couleur du thème courant) et réinjecter les données cachées.

`buildDepartmentsLineLayer` pose **`maxzoom: 9`** sur le layer : l'overlay est masqué dès z≥9, là où le fond OpenFreeMap porte lui-même `admin_level=6` (géométrie fine) — on bascule sur ce tracé natif au lieu de superposer notre GeoJSON simplifié (évite le double trait à fort zoom). L'overlay ne couvre donc que z5-8 (l'échelle France où le fond est muet).

Le fichier `static/departements.geojson` est **bundlé** (évite le CORS). Il est **dérivé d'OpenStreetMap** (`admin_level=6`, même famille de données que le fond OpenFreeMap → bon raccord avec les côtes/régions/frontières du fond), simplifié (mapshaper Visvalingam ~0,4 %) et arrondi à 5 décimales : ~200 KB / ~70 KB gzip, 100 features (métropole + Corse 2A/2B + Rhône/Métropole de Lyon 69D/69M + DOM 971/974/976). **Pourquoi pas la couche `boundary` du fond** : OpenFreeMap ne porte `admin_level=6` qu'à partir du **zoom 9** (vérifié en décodant les tuiles MVT) — invisible à l'échelle France (z5-8, zoom par défaut ~5,2). Régénération : voir l'en-tête de `DEPARTMENTS_GEOJSON_URL` dans `constants.ts` (Overpass `area FR` + `admin_level=6` → `osmtogeojson` → `mapshaper -simplify -o precision`). Réutiliser ce pattern (source geojson dédiée) pour tout nouvel overlay autonome (régions, communes…).

## Playback (lecture en direct)

Le bouton play/pause de la barre de run (`src/lib/components/time/playback-button.svelte`, monté
dans `time-selector.svelte` à côté du bouton de préchargement) anime les échéances **en direct** —
pas de pré-rendu. Le moteur `src/lib/playback-engine.ts` (`createPlaybackEngine`, dépendances
injectées, testé dans `tests/playback-engine.test.ts`) avance le store `time` d'un pas via le
callback `playbackAdvance` de `time-selector.svelte` (store + URL + `changeOMfileURL()` + centrage,
**sans** `checkClosestModelRun` : les échéances sortent des `valid_times` du run courant), attend
que la frame soit réellement rendue (événement `commit` de `slot-events.ts` ; les commits
surnuméraires des managers raster/vecteur sont ignorés pendant qu'une avancée est programmée) puis
programme la suivante avec un plancher de 1,2 s/frame (`PLAYBACK_MIN_FRAME_MS`) et une garde de
10 s sans commit (`PLAYBACK_MAX_WAIT_MS` — on avance quand même). La **plage lue** est celle du
sélecteur de mode partagé avec le préchargement (store persisté `prefetchMode`,
`src/lib/stores/prefetch.ts`, défaut « Run complet ») : bornes injectées au start via `getBounds`,
boucle dans la plage (`nextPlaybackFrame`, `src/lib/playback.ts`) jusqu'à pause, saut au début de
plage si l'échéance courante est dehors. Changer de plage en cours de lecture redémarre le moteur
sur les nouvelles bornes (`$effect` untracked — `start()` lit `$time`/`$metaJson`, ne pas
re-déclencher sur chaque frame). Arrêt automatique sur `error` de slot et sur changement de
domaine/run. Au play, le bouton lance aussi un `prefetchData()` **en arrière-plan** sur la même
plage (variable affichée), fire-and-forget et annulé à la pause (`AbortController`) : la lecture
démarre sans attendre et se lisse à mesure que le cache rattrape, en plus de `neighbor-prefetch.ts`
et du préchargement manuel.

L'ancien player **pré-rendu** (diaporama : capture canvas, overlay, gel de la carte) reste retiré.
Vestige : `src/lib/playback-renderer.ts` ne contient plus que `waitForIdle(map, timeoutMs, signal?)`,
utilisé par `capture-flow.svelte` pour attendre la mise au repos de la carte avant la capture PNG du
canvas (`preserveDrawingBuffer` reste activé sur la map — voir `+page.svelte`).

**Préchargement (prefetch) — réintroduit seul.** `src/lib/prefetch.ts` + `src/lib/components/time/prefetch-button.svelte` ont été restaurés (sans le player d'animation). Le bouton vit dans la barre de run (`time-selector.svelte`, dans le `<div>` `-top-4.5` à côté du sélecteur de run) : un `Select` de mode (Aujourd'hui / 24 h suivantes / 24 h précédentes / Run complet — store persisté `prefetchMode`, partagé avec la lecture, libellés dans `PREFETCH_MODE_LABELS` de `prefetch.ts`) + un bouton télécharger qui appelle `prefetchData()`. `getDateRangeForMode()` traduit le mode en plage `[startDate, endDate]`, `prefetchData()` filtre les `valid_times` du `metaJson` dans cette plage et précharge chaque pas via `omFileReader.prefetchVariable()` (8 workers concurrents, annulable via `AbortController`). Sans `metaJson`/`modelRun` chargés, un toast d'avertissement s'affiche.

**Préchargement automatique des échéances voisines (#46).** `src/lib/neighbor-prefetch.ts`
s'abonne au store `time` (initialisé dans `+page.svelte`), debounce
`NEIGHBOR_PREFETCH_DEBOUNCE_MS` (400 ms), détecte le sens de navigation via les index
`valid_times` et précharge une fenêtre asymétrique (`computeNeighborWindow` : 3 devant /
1 derrière dans le sens, ±1 sur saut/premier chargement) de la variable affichée — et de
`variable2` si `layer2Enabled` — via `prefetchData()`. Un seul préchargement en vol
(`AbortController`, annulé à chaque nouveau changement). Les contours/flèches partagent la
variable principale → couverts sans requête dédiée. Remplace l'ancien préchargement
header-only du `postReadCallback` (`getNextOmUrls`, retiré).

**Après la frame courante.** `triggerPrefetch` attend que le store `loading` repasse à
`false` (`whenIdle`) avant de lancer quoi que ce soit : au démarrage, le préchargement
partait pendant le chargement de la frame courante et lui disputait les connexions vers le
stockage (31 requêtes `.om` avant le premier affichage, contre ~12 désormais).

**Décode anticipé des voisins (action 1, perf scrubbing).** Au-delà des octets chauffés par
`prefetchData()`, `triggerPrefetch` **décode** ensuite chaque échéance voisine via
`omProtocol({ url: neighborDecodeRequestUrl(getOMUrlFor(variable, neighborTime, { arrows: false, contours: false, grid: false })), type: 'arrayBuffer' }, …)`.
C'est une tuile vectorielle `/0/0/0` sans flèches, isolignes ni grille : le package lit les
données puis renvoie une tuile vide sans passer par le worker de rendu. **Piège** : une
requête `type: 'json'` (TileJSON) ne lit plus les données depuis `weather-map-layer` 0.3.0.
Le décode anticipé était donc inopérant jusqu'à ce correctif. Il peuple `state.data` dans le `stateByKey` de l'instance partagée (`getProtocolInstance`,
rétention `maxStatesWithData: 24` dans `omProtocolSettings`, contre 2 par défaut dans le package). Un saut ultérieur vers ce voisin réutilise la frame
décodée au lieu de refaire la lecture + le décode. **L'URL est bâtie via le même
`getOMUrlFor(variable, timeOverride)` que la source MapLibre** (`'om://' + getOMUrl()`). La clé du
`stateByKey` ne garde que les paramètres de `DATA_RELEVANT_PARAMS` (aujourd'hui `variable`) :
retirer flèches/isolignes/grille de l'URL de décode ne change donc pas la clé. `getOMUrlFor`
accepte un `timeOverride?: Date` (défaut = `get(time)`) pour construire l'URL d'une autre
échéance sans toucher au store. Quelles échéances décoder : `neighborTimesToDecode()` (fenêtre,
courante exclue, plus proche d'abord). Décode séquentiel, abortable, erreurs silencieuses.
**Impact mesuré** (Chromium headless, AROME France, octets déjà en cache) : pas suivant affiché en
**~75 ms** décodé contre ~105 ms non décodé ; frame froide avec réseau ~1,5-2 s. **Limite** : le décode anticipé
s'abonne à `time` seulement → un **changement de variable** ne le re-déclenche pas, donc le
1ᵉʳ pas d'heure après un changement de variable reste froid (puis se réchauffe).

## Domain allowlist (Infoclimat preset)

`MODEL_SELECTOR_GROUPS` in `src/lib/constants.ts` is the single source of truth for the
domain selector (`model-selector.svelte`): it declares the visible domains, their order,
their group, and their display label — French models first (issue #48). `DOMAIN_ALLOWLIST`
is **derived** from it (flattened domain values). The selector iterates this table directly;
it no longer relies on the package's `domainGroups` + `startsWith(group.value)` grouping
(which could not merge AROME HD / France / OM under one group). Labels are aligned onto
`domainOptions` via `applyModelSelectorLabels()` (`src/lib/model-selector-labels.ts`, called
in `stores/variables.ts`) so the trigger button and the dropdown agree. This is still
**display-only**: URLs sharing a non-listed domain resolve correctly. Add/reorder entries in
`MODEL_SELECTOR_GROUPS` to change the UI.

## Métadonnées de run (`metadata.ts`) et changements de domaine

`getInitialMetaData()` lit `latest.json` et `in-progress.json` du domaine sélectionné et les écrit dans les stores **globaux** `latest`/`inProgress` ; `getMetaData()` choisit le run (`modelRun`, défaut = `latest`) et lit au besoin le `meta.json` d'un run passé. Ces requêtes sont asynchrones et un changement de domaine ne les annule pas : **chaque réponse est reliée à sa sélection** par un compteur module-level `domainSelection`, incrémenté à chaque valeur du store `domain`. Une réponse arrivée après un changement de domaine n'écrit rien (`getInitialMetaData()` renvoie `false`, y compris sur erreur HTTP) ; `getMetaData()` lève `StaleMetadataError` si le domaine **ou** le run a changé pendant la lecture du `meta.json`. Les appelants (`+page.svelte`, `time-selector.svelte`) s'arrêtent alors sans écrire `metaJson`. Le relevé périodique (`+layout.svelte`, 5 min) ne change pas la sélection et ne rend donc pas périmé un chargement en cours. **Bug corrigé** : à l'ouverture d'un lien `?domain=…`, la réponse tardive du domaine précédent (AROME, run 12Z) écrasait `latest` du nouveau (ECMWF IFS, run 06Z) → run inexistant, `meta.json` 404, fond vide. Tests de concurrence pilotés à la main : `tests/metadata-race.test.ts`.

## Pseudo-domaines servis depuis le bucket R2

Certains domaines ne viennent pas d'Open-Meteo mais d'un bucket R2 (`VITE_MODELS_BUCKET_URL`, voir `getModelsBucketUrl()`) : ils sont listés dans `BUCKET_DOMAINS` (`src/lib/helpers.ts → getBaseUri()`) et enregistrés via un module dédié appelé depuis `stores/variables.ts`, **gated** sur la présence du bucket (invisibles dans le sélecteur sinon). Aujourd'hui : `anomaly_europe` (`anomaly-domain.ts`, layout `/anomaly/…` → resolver custom dans `om-protocol-settings.ts`), les cinq AROME-OM `arome_om_{reunion,antilles,guyane,ncaledonie,polynesie}` (`arome-om-domain.ts`, table data-driven `AROME_OM_TERRITORIES` — même modèle 0,025° et mêmes 12 variables de surface, ne diffèrent que par l'emprise ; grilles tirées de `infoclimat-pipelines/crates/core/src/grid.rs`), `arome_france_convection` (`arome-france-convection-domain.ts`), `arome_france` (`arome-france-domain.ts`), `arome_france_hd` (`arome-france-hd-domain.ts`) et `ecmwf_ifs_0p1` (`ecmwf-ifs-0p1-domain.ts` — ECMWF IFS open data 0,1° mondial, grille régulière 3600×1801, `3_hourly`/`6_hourly`, pression déjà en hPa : ne **pas** lui étendre la division `/100` réservée à `ecmwf_ifs` dans `postReadCallback` ; échelles dédiées par clé exacte pour `relative_vorticity_500hPa` — ×1e5 dans `postReadCallback`, ×10⁻⁵ s⁻¹ divergente — et `surface_pressure` (hPa) : sans elles, la résolution par préfixe les envoyait sur `relative_humidity` (%) et `temperature` (°C). Toute nouvelle variable d'un domaine maison doit être vérifiée via `getColorScale`). Tous sauf l'anomalie utilisent le layout `data_spatial/{domain}/…` standard → resolver par défaut, aucune modif du protocole.

`arome_france_convection` (AROME France métropole, convection/orage) expose 10 variables avec colormaps dédiées dans `src/lib/color-scales/` (8 continues — `radar_reflectivity`, `brightness_temperature`, `brightness_temperature_wv`, `cape`, `convective_inhibition`, `visibility`, `lightning_density`, `precipitable_water` (mm) — + 1 catégorielle partagée par `precipitation_type`/`precipitation_type_severe`, type `CategoricalColorScale` rendu par `components/scale/categorical-legend.svelte`). **Toutes** sont enregistrées par clé exacte dans `standardColorScales` (`om-protocol-settings.ts`) : sans ça, la résolution par famille du package les retombe sur le fallback `temperature` (°C) — c'était le bug de `precipitable_water`, ajoutée côté producteur sans échelle et dont la légende affichait des °C (cf. § _Résolution des échelles de couleurs_). La variable affichée par défaut sur bascule de domaine est pilotée par `DOMAIN_DEFAULT_VARIABLES` (`constants.ts`), consultée par `matchVariableOrFirst()` (`metadata.ts`).

`arome_france` (AROME France métropole) expose ~50 variables servies depuis le bucket maison — **pas de fallback Open-Meteo** : les 12 variables de surface historiques (`temperature_2m`, `relative_humidity_2m`, `dew_point_2m`, `wind_u_component_10m`, `wind_v_component_10m`, `wind_gusts_10m`, `pressure_msl`, `cloud_cover_low/mid/high`, `precipitation`, `precipitation_sum`) **plus** des niveaux iso-pression (geopotential*height / relative_humidity / temperature / vent u-v aux niveaux 300/500/700/850/925/1000 hPa + `geopotential_height_pv1500`), des indices (`humidex`, `wind_chill_2m`, `freezing_level_height`), des extrêmes/cumuls (`temperature_2m_max/min`, `wind_gusts_10m_max`, `snowfall_sum`) et des champs dérivés (`theta_e_850hPa` en K, `theta_w_850hPa` en °C, `thickness_500_1000hPa` en gpm, `absolute_vorticity_500hPa`). Le sélecteur de variables se construit dynamiquement à partir de `latest.json` (`chrome/layer-list.svelte` via `buildVariableList()`/`buildLevelGroups()` de `src/lib/layer-list.ts`), donc l'ajout de variables côté producteur ne demande **aucune liste codée en dur** côté domaine. Même grille que `arome_france_convection` (1121×717 à 0,025°). Colormaps : défauts du package pour les surfaces/niveaux standard, surchargées par clé exacte dans `standardColorScales` (`om-protocol-settings.ts`) pour `precipitation_sum`, `snowfall_sum` (cm), `theta_e_850hPa` (K), `theta_w_850hPa` (°C), `thickness_500_1000hPa` (gpm), `absolute_vorticity_500hPa` et `geopotential_height_pv1500` (m) — sans quoi la résolution par famille du package les mapperait sur le fallback `temperature` (°C), ou sur les bornes 500 hPa de `geopotential_height` (4600-6000 m, bien trop étroites pour la tropopause) dans le cas de `pv1500`. Le tourbillon absolu est diffusé en s⁻¹ (~1e-4) et **mis à l'échelle ×1e5 dans `postReadCallback`** (`om-protocol-settings.ts`, gaté `domain === 'arome_france' && variable === 'absolute_vorticity_500hPa'`) pour une légende lisible en ×10⁻⁵ s⁻¹ (même mécanisme que le `pressure_msl / 100` ECMWF). Les libellés FR des variables hors `variableOptions` du package sont mappés par clé dans `i18n/variables-fr.ts`. Le vent u/v est dérivé en vitesse/direction par le package (le `_v_component` est masqué par `groupVariablesByCategory()`, `src/lib/layer-list.ts`), donc aucune dérivation côté client. Dans le sélecteur, `arome_france` et `arome_france_convection` apparaissent sous le groupe « Météo-France Arome » défini par `MODEL_SELECTOR_GROUPS` (`constants.ts`) — voir le § \_Domain allowlist*. Le groupe partagé `AROME_FRANCE_GROUP` (« AROME France (Infoclimat) ») poussé dans `domainGroups` par `ensureAromeFranceGroup()` (`arome-france-domain.ts`) n'est **plus consommé pour l'affichage** (vestige conservé, couvert par tests).

**`weather_ai_wnc_mini` (Weather AI, modèle IA expérimental) — bucket distinct.** Champs continus du modèle WeatherNext Cyclones Mini (Google DeepMind) exportés en `.om` par le producteur weather-ai (`scripts/wn2/om_publish.py`, #266) au layout `data_spatial/{domain}/…` standard, mais sur **son propre bucket** : `getBaseUri()` (`helpers.ts`) le route vers `getWeatherAiOmBucketUrl()` (`VITE_WEATHER_AI_OM_BUCKET_URL` au build, `WEATHER_AI_OM_BUCKET_URL` au runtime Docker) au lieu de `getModelsBucketUrl()`, et `registerWeatherAiDomain()` (`weather-ai-domain.ts`) n'enregistre le domaine que si cette variable est fixée — il n'est donc **pas** dans `BUCKET_DOMAINS`. Grille globale 1° `{nx: 360, ny: 181, latMin: −90, lonMin: −180, dx = dy = 1}` (lignes du sud au nord, colonnes −180..179, pas de colonne +180 : bouclage antiméridien par `|dx|·nx == 360`), `time_interval`/`model_interval` `6_hourly` (+6 h → +72 h, pas d'échéance 0). Variables (lues dans `latest.json`, aucune liste codée en dur pour le sélecteur) : `pressure_msl` en hPa (échelle `pressure` du package, isobares comme les autres modèles), `cyclone_existence_probability` publiée en fraction 0..1, **ramenée en % dans `postReadCallback`** (gaté domaine + variable) et coloriée par la clé exacte `cycloneExistenceProbabilityScale`, `temperature_2m` en °C (échelle `temperature` du package) et, depuis weather-ai#318, `precipitation` — **cumul en mm sur les 6 h précédant l'échéance** (facteur OM 10), que le package divise par le pas (`delta_time_hours=6`, y compris à +6 h : `timeStepHoursAt` prend l'écart à l'échéance suivante ; avec une seule échéance publiée — première échéance d'un run progressif — il renvoie `undefined` et `fallbackTimeStepHours` (`weather-ai-domain.ts`) fournit les 6 h du domaine) : la carte montre un **taux moyen en mm/h**, libellé « taux moyen sur les 6 h précédentes » dans `chrome/context-strip.svelte` (`weatherAiVariableNote`), échelle `precipitation` du package — et `wind_u_component_10m` / `wind_v_component_10m` (m/s, facteur 100 ; vitesse, direction et flèches dérivées par le package comme pour les autres modèles, flèches 10 m en repli via `deriveDisplayedWindLevel`). **Runs sans vent ni précipitation** : les anciens runs (reçu `om-maps-receipt/1`) n'ont que `temperature_2m` ; rien n'est codé en dur, le sélecteur suit `variables`, les flèches de repli ne sont demandées que si `wind_u_component_10m` est publié, et un changement de run (`time-selector.svelte`) appelle `matchVariableOrFirst()` : une variable absente du run choisi retombe sur `pressure_msl` au lieu d'une lecture en erreur. Pour ce domaine seulement, entre le changement de `modelRun` et l'arrivée du `meta.json` du run choisi, `getOMUrlFor` ne bâtit **aucune URL** (`metaJson.reference_time` ≠ `modelRun`) : choisir le vent ou la précipitation dans cet intervalle, avec le sélecteur encore nourri par les variables du run précédent, ne charge rien ; la fin de la lecture recharge les couches. Le choix d'un run passe par `loadModelRun()` (`metadata.ts`) : si son `meta.json` échoue (404, réseau), le **dernier couple (run, `metaJson`) chargé avec succès** est restauré — pas celui capturé au départ, bancal si une autre sélection était en vol (A puis B : `modelRun` = A, `metaJson` = R) — (sinon la garde bloquait toute URL jusqu'au choix d'un autre run) et `time-selector.svelte` affiche un toast. Un compteur `runSelection` relie chaque requête à sa sélection : seule la dernière applique ou restaure, toute autre lève `StaleMetadataError` sans rien écrire (A → B → A : l'échec tardif de la 1re A ne défait pas la 2de ; tests : `tests/metadata-race.test.ts`). Chaque nouvelle variable doit avoir une échelle par clé exacte ou de famille (cf. § _Résolution des échelles de couleurs_) et être ajoutée à `WEATHER_AI_FIELDS` (`weather-ai-domain.ts`, libellé + variables `.om`), la liste que l'onglet Cyclones IA annonce (« Pression au niveau de la mer, … : modèle « Weather AI (WeatherNext) » de l'onglet Données », affichée dès que le modèle est enregistré) : `weatherAiFieldLabels` n'y garde que les champs dont toutes les variables figurent dans `variables` du `latest.json` public (`watchWeatherAiVariables` : `fetchWeatherAiVariables` au montage de l'onglet puis à chaque `METADATA_REFRESH_INTERVAL` ; un échec garde la dernière liste, réponses dépassées ignorées ; sans aucune réponse, les trois champs de tous les runs). Publication progressive : `in-progress.json` peut porter `completed: false` et les seules échéances déposées — `getMetaData()` le lit tel quel, sans `meta.json` (déposé en fin de run). **Premier run** : `latest.json` n'est déposé qu'après la 12ᵉ échéance ; pour ce domaine seulement (`FIRST_RUN_FROM_IN_PROGRESS`, `metadata.ts`), un **404** de `latest.json` fait tenir `in-progress.json` lieu de dernier run (run par défaut limité aux échéances déposées), jusqu'à la parution de `latest.json` au relevé suivant. Si `in-progress.json` est absent ou sans échéance, `getInitialMetaData()` lève `DomainUnavailableError` : `+page.svelte` affiche un toast (« aucune échéance publiée… Retour à <modèle> ») et revient au dernier domaine chargé (ou `DEFAULT_DOMAIN`), via `createDomainLoader` (`domain-load.ts`) : chaque sélection porte une génération, et toute réponse d'une sélection dépassée est ignorée (`stale`) : « indisponible », autre erreur HTTP, ou `false` de `getInitialMetaData()` (garde `domainSelection`, cf. § _Métadonnées de run_). Weather AI puis ECMWF : le 404 tardif de Weather AI n'annule pas ECMWF ; un chargement dépassé ne devient pas le modèle de repli (tests A → B → A, repli puis sélection manuelle, échec HTTP tardif dans `tests/domain-load.test.ts`). Le repli premier run applique les mêmes gardes avant tout `loading.set` ou `throw` et renvoie `true`. Toute autre réponse (403, 500…) reste une erreur, et les autres domaines gardent l'exigence des deux fichiers. Pas de météogramme (absent de `DOMAIN_TO_API_MODEL`). Mentions obligatoires : pas de bandeau sous le sélecteur de modèle (réservé aux trajectoires, onglet Cyclones IA). `SlotManager` déclare sur chaque source `om://` l'attribution de `omSourceAttribution(sourceUrl)` (`weather-ai-domain.ts`) : pour une URL du domaine, `WEATHER_AI_ATTRIBUTION` à l'identique plus un lien « Sources et licence », affichés dans la notice compacte MapLibre (« i ») tant qu'une couche Weather AI est à l'écran et retirés avec la source au changement de modèle. Le lien ouvre `components/weather-ai/weather-ai-sources-dialog.svelte` (licence, non-responsabilité ECMWF, mention Google, DOI Copernicus). Badge « Expérimental » dans `chrome/context-strip.svelte` et mention « expérimental » de la description du modèle. Tests sur une fixture `.om` générée avec les réglages du producteur (run 00Z ancien, sans vent ni précipitation ; run 06Z avec `precipitation` et vent u/v) : `tests/weather-ai-domain.test.ts`, `tests/fixtures/weather-ai-om/generate_fixture.py`.

## Variables catégorielles (`CATEGORICAL_VARIABLES`)

Les variables dont les valeurs sont des **codes entiers** (pas un champ continu) ne peuvent pas être échantillonnées en bilinéaire : une valeur interpolée entre deux codes éloignés atterrit sur un code intermédiaire arbitraire (halos de catégorie parasite en lisière, valeurs non entières au survol). Depuis `@openmeteo/weather-map-layer@0.2.0`, `RenderOptions.interpolation` expose `'nearest' | 'linear' | 'cubic' | 'monotone'` (défaut `linear`) — ce qui manquait historiquement. `CATEGORICAL_VARIABLES` (`constants.ts`) liste ces variables et `getOMUrlFor()` (`src/lib/url.ts`) ajoute `&interpolation=nearest` à leur URL `om://`. Le paramètre est lu **à la fois** par le rasterizer worker (`renderOptions.interpolation`) et par `getValueFromLatLong()` (popup), donc les deux chemins sont couverts sans toucher au fork.

Ces variables portent une `CategoricalColorScale` (`color-scales/types.ts`) : `breakpoints` = codes triés croissants, `colors` et `categories` alignés index par index. La légende bascule automatiquement en mode catégoriel — `scale.svelte` teste `isCategorical(colorScale)` (présence du champ `categories`), sans connaître le nom de la variable. Aujourd'hui : `weather_code` (codes WMO 4677, `color-scales/weather-code.ts`, libellés FR importés de `meteogram/weather-symbols.ts` — source unique) et `precipitation_type`/`precipitation_type_severe`.

**`precipitation_type` / `precipitation_type_severe` toujours masquées.** Elles restent dans `HIDDEN_VARIABLES` (`constants.ts`, filtré par `buildVariableList()` dans `src/lib/layer-list.ts`) : le mécanisme nearest les couvre désormais (y compris pour une URL partagée, le masquage étant display-only), mais le démasquage reste à valider visuellement. Suivi : [issue #35](https://github.com/cmer81/maps/issues/35).

## Résolution des échelles de couleurs — le fallback `temperature`

`getColorScale(variable, isDark, colorScales)` du package résout dans cet ordre : clé exacte → famille (`mot0_mot1`, puis `mot0`) → cas spéciaux (`geopotential_height`, suffixes `mean`/`max`/`min`/`anomaly`) → **`colorScales.temperature`**. Ce dernier maillon est un fallback **silencieux** : toute variable sans clé ni famille est coloriée comme des degrés Celsius, et comme la légende (`scale.svelte`) et le popup (`popup.ts`) lisent `colorScale.unit`, ils affichent « °C ». C'est la cause racine d'une famille de bugs récurrents (`precipitable_water`, `wind_chill_2m`, les `*_sum`, puis l'onglet « Autres » des domaines upstream). **Toute variable ajoutée côté producteur doit donc être enregistrée par clé exacte dans `standardColorScales`** (`stores/om-protocol-settings.ts`), même quand une échelle du package semble s'appliquer : certaines clés du package existent mais portent des bornes sans rapport (`sensible_heat_flux`/`latent_heat_flux` annoncent W/m² sur les breakpoints de `temperature` ; `soil_moisture` annonce « vol. % » sur une donnée en m³/m³ ; `visibility` annonçait W/m² sur 4600-6000).

**Ne pas juger une échelle du package sur ses bornes seules.** Ses `breakpoints` ne sont pas équirépartis : la palette peut concentrer ses paliers là où la donnée vit, même quand les extrêmes paraissent aberrants. `freezing_level_height` / `snowfall_height` s'étalent nominalement sur −5200…5200 m, mais 33 de leurs 42 paliers couvrent 0…5200 m tous les 160-200 m — les resserrer dégraderait la résolution. Le critère qui tranche est le **taux de saturation mesuré** sur un `.om` réel (part des pixels hors bornes) : 0 % pour ces deux-là, contre 32 % (`sensible_heat_flux`) et 70 % (`latent_heat_flux`), qui justifient eux une échelle dédiée. Les tests de `tests/upstream-color-scales.test.ts` verrouillent les deux sens (couverture des extrêmes mesurés **et** finesse d'échantillonnage de la bande utile).

**Conventions de signe divergentes entre producteurs.** Les `colorScales` sont indexées par **nom de variable**, jamais par domaine : une seule échelle sert donc tous les domaines qui publient la variable. Quand deux producteurs n'utilisent pas la même convention, c'est la **donnée** qu'il faut normaliser dans `postReadCallback`, pas l'échelle. Cas traité : `convective_inhibition`, publié **négatif** par `arome_france_convection` (mesuré −267…+10) et **positif** par les domaines upstream (`dwd_icon_d2` 0…295, `dwd_icon_eu`, `meteoswiss_icon_ch1/ch2`, `ncep_gfs025`) — `postReadCallback` applique `Math.abs` (magnitude du couvercle) et l'échelle est positive. Sans ça, l'échelle négative taillée pour AROME renvoyait toute valeur positive sur son dernier breakpoint (transparent) : le CIN était **invisible** sur les cinq domaines upstream.

## Échelle de cumul de précipitations 0,1 → 500 mm (ECMWF)

`precipitation_sum` (cumul du run) a son échelle dédiée `precipitationSumScale` (`src/lib/color-scales/precipitation.ts`, clé exacte dans `standardColorScales`) ; les cumuls `precipitation_sum_Nh` du worker en héritent par la résolution par famille. La pluie par pas de temps (`precipitation`, `rain`, `showers`) garde **volontairement** l'échelle `precipitation` du package. Elle est calquée sur la légende ECMWF « Accumulated total precipitation » et compte 26 paliers : 0,1 · 1 · 2 · 3 · 5 · 7 · 10 · 15 · 20 · 25 · 30 · 40 · 50 · 60 · 70 · 80 · 90 · 100 · 125 · 150 · 175 · 200 · 250 · 300 · 400 · 500 mm (gris au-delà). Les couleurs ont été relevées à l'œil sur la légende ECMWF. Un seul écart à l'ECMWF, qui est opaque : les quatre premières classes gardent une transparence progressive. La classe 0 (< 0,1 mm) reste transparente. Historique et alternatives écartées (paliers par durée, palette Infoclimat) : `specs/001-lisibilite-cumuls-pluie/`.

- **Classe 0 transparente** : sous le premier breakpoint, le moteur applique `colors[0]` (`Math.max(0, idx)`), **pas** la transparence. L'échelle commence donc par `0 → alpha 0`. L'ancienne échelle `precipitation_sum` teintait H0 à tort.
- **Aplats discrets** : ne pas émettre `color_blend=true` (option 0.2.0 d'interpolation continue entre couleurs) pour ce cumul.
- **Hors périmètre, volontairement inchangés** : `precipitation`, `rain`, `showers` et `snowfall_water_equivalent` gardent l'échelle `precipitation` du package (en mm/h, voir ci-dessous) ; `graupel_sum`, `snow_graupel_sum` et `snowfall_water_equivalent_sum` gardent ses paliers et couleurs, avec l'unité ramenée en mm (`waterEquivalentSumScale`) ; `snowfall_sum` garde son échelle en cm.

## Pluie par pas de temps en taux horaire (`delta_time_hours`)

Depuis `weather-map-layer` 0.3.0, le reader renvoie `precipitation`, `rain`, `showers`, `snowfall`, `snowfall_water_equivalent` (et leurs `_mean`/`_spread`) **en taux horaire** : il divise le cumul stocké sur le pas par la durée du pas. Cette division n'est pas désactivable. Il lui faut la durée du pas, passée dans l'URL `om://` par `&delta_time_hours=…` : sans elle, la lecture est **rejetée** (calque vide, popup sans valeur). `getOMUrlFor` (`src/lib/url.ts`) l'ajoute pour toute variable où `variableUsesTimeStep(variable)` est vrai, à partir de `timeStepHoursAt(échéance, metaJson.valid_times)`, ou de `fallbackTimeStepHours(domaine)` quand une seule échéance est connue (Weather AI : 6 h) ; l'échéance est celle demandée (`timeOverride`), pas celle du store. Sur le domaine Weather AI, si `metaJson` décrit un autre run que `modelRun` (`meta.json` du run choisi en cours de lecture), `getOMUrlFor` renvoie `undefined`. Le préchargement d'octets (`prefetch.ts`, `prefetchVariable`) n'en a pas besoin. Les cumuls depuis le run (`precipitation_sum`, `*_sum`) ne sont pas concernés. Côté affichage, l'unité `mm/h` relève de la catégorie précipitations (`stores/units.ts`) : conversion en pouces et suffixe « /h » conservé (`mm/h`, `inch/h`).

## Sondage vertical (Skew-T)

`src/lib/sounding/` implémente un sondage atmosphérique client-side en trois couches indépendantes :

1. **Lecture** (`column.ts`) — `fetchColumn()` reprend le reader partagé du protocole (`getProtocolInstance(settings).omFileReader`) et appelle `readRawVariable(omUrl, variable, ranges)` pour chaque variable (température, humidité, vent U/V) sur une petite bbox autour du point cliqué, avec interpolation bilinéaire. Depuis `weather-map-layer` 0.1.0 la lecture est **atomique** (fichier + variable en un seul appel) : plus d'état « fichier courant » partagé, donc plus de course entre appelants. On utilise `readRawVariable` (et non `readVariable`) pour récupérer les champs **bruts** : `readVariable` applique des règles de dérivation qui transforment les composantes de vent en vitesse+direction, alors que le sondage a besoin des U/V séparés (et les reconstituer supposerait d'interpoler une direction, faux à la couture 0°/360°). Le choix du `WeatherMapLayerFileReader` est délibéré : `getValueFromLatLong()` ne retourne la valeur que pour la variable actuellement rendue ; ici on lit les niveaux de pression indépendamment. Le cache bloc-byte du reader, partagé avec le rendu des tuiles, évite un re-téléchargement du `.om` (même mécanique que `src/lib/prefetch.ts`).
2. **Calcul** (`thermo.ts`, `parcel.ts`, `indices.ts`, `skewt-coords.ts`) — fonctions pures TypeScript sans dépendance au domaine : primitives Bolton/Magnus, adiabates, bulbe humide, parcelle SB & MU (LCL/LFC/EL), CAPE/CIN/LI, LPN/isothermie, cisaillement 0-1/0-3/0-6 km, et la transformation log-P + inclinaison du Skew-T.
3. **UI** (`src/lib/components/sounding/`) — panel tabulé réactif sur le scrubber de temps (debounce + jeton de génération pour annuler les fetch obsolètes).

La couche lecture est source-agnostique : `SOUNDING_LEVELS_BY_DOMAIN` dans `src/lib/constants.ts` mappe chaque domaine **source** vers ses niveaux de pression disponibles ; le domaine `arome_om_reunion` (Réunion) est anticipé dans la table mais pas encore exposé dans l'UI.

**Domaine affiché ≠ domaine source du sondage.** Certains domaines affichés ne diffusent pas eux-mêmes les niveaux de pression : `SOUNDING_SOURCE_BY_DOMAIN` redirige alors le sondage vers un autre domaine sur **la même grille**. Aujourd'hui `arome_france` (pseudo-domaine bucket maison Infoclimat) → `meteofrance_arome_france0025` (AROME 0,025° d'Open-Meteo, grille identique 1121×717 @ 0,025°, 24 niveaux iso-pression). La redirection est **conservée** même si `arome_france` publie désormais quelques niveaux iso-pression (300/500/700/850/925/1000 hPa) : ces 6 niveaux ne suffisent pas à reconstruire une colonne de sondage (24 niveaux requis, cf. `SOUNDING_PRESSURE_LEVELS_HPA`). `soundingSourceDomain()` résout la redirection (identité par défaut) ; `isSoundingDomain()` et `soundingLevelsForDomain()` raisonnent sur la source. Quand la source diffère de l'affiché, `column.ts → doFetchColumn()` lit le run de la source via son propre `latest.json` (`fetchSoundingSourceRun()` — le store `modelRun` ne porte que le run de l'affiché) et bâtit l'URL `.om` avec `buildSoundingOmUrl()` (`helpers.ts`) sur la grille de la source. Ajouter un nouveau domaine : éditer `SOUNDING_LEVELS_BY_DOMAIN` (s'il porte ses niveaux) ou `SOUNDING_SOURCE_BY_DOMAIN` (s'il faut rediriger), rien d'autre.

Le bouton « Sondage vertical » du popup n'est affiché que si `isSoundingDomain(domaine)` (domaine dont la **source** est listée dans `SOUNDING_LEVELS_BY_DOMAIN` — AROME 0,025° en direct, ou `arome_france` via sa redirection) **et** si le toggle persisté `soundingButtonEnabled` (réglages → `sounding-settings.svelte`) est activé. Sur les autres modèles le bouton est masqué (`display:none` dans `updatePopupContent`).

## Meteogram / Espace point

`src/lib/meteogram/` + `src/lib/components/point-workspace/` implémentent un « espace point » : un tiroir bas ouvert depuis le popup, dont le premier module est un meteogram temporel. Contrairement au sondage vertical (qui lit le `.om` en cours via `WeatherMapLayerFileReader`), le meteogram **ne lit pas les OMfiles S3** : il interroge l'**API JSON publique** `api.open-meteo.com/v1/forecast` (`src/lib/meteogram/api.ts → buildForecastUrl/fetchMeteogram`, `timezone=auto` + `wind_speed_unit=ms`), **une requête par point** (pas de pré-agrégation, pas de worker). **Heure locale du point** : `timezone=auto` fait renvoyer les timestamps en heure locale + `utc_offset_seconds` + `timezone` (IANA). `parseForecast()` **reconstruit des instants UTC absolus** via l'offset (`parseLocalTimes`) — indispensable au couplage avec la carte, dont les `valid_times` sont en UTC — et expose `timezone`/`utcOffsetSeconds` dans `MeteogramData`. L'**affichage** local (axe des heures, séparateurs de jours à **minuit local**, tooltip) est délégué à Highcharts via `time.timezone = data.timezone` (`buildChartOptions`), qui gère le DST. `fetchBorrowSource` (emprunt AROME HD) reparse avec le même offset pour rester aligné par instant. _Limite DST connue_ : l'offset est unique par requête ; une bascule heure d'été/hiver dans la fenêtre 7 j décalerait d'1 h les pas au-delà de la transition (edge case accepté). `HOURLY_VARIABLES` fixe les 9 variables demandées (température, point de rosée, précipitations, vent 10 m vitesse/rafales/direction, pression, `weather_code`, `is_day`). `parseForecast()` indexe défensivement chaque série sur `hourly.time` (une variable absente de la réponse devient un tableau de `null`, jamais `undefined`). `fetchMeteogram()` applique ensuite `trimTrailingNulls()` : l'API renvoie un axe de **7 jours par défaut** mais un modèle à horizon court (AROME HD ~51 h) laisse le reste en `null` — sans rognage l'axe temps s'étirerait sur 7 jours avec les courbes tassées dans le premier tiers. On borne donc la série au dernier pas réellement renseigné.

Le domaine affiché n'est pas forcément un `models=` valide côté API publique : `DOMAIN_TO_API_MODEL` (`constants.ts`) mappe les domaines app → identifiants API, résolu par `resolveApiModel()`/`hasMeteogram()` (`src/lib/meteogram/model-map.ts`). Un domaine absent de la table masque le bouton « Meteogram » du popup (`popup.ts`) — c'est le cas des pseudo-domaines bucket maison (`arome_france`, `arome_france_convection`) et de `anomaly_europe`, non exposés par l'API publique. **Piège du préfixe `ncep_`** : c'est la convention des domaines du bucket S3, **pas** un identifiant `models=` — l'enum `MultiDomains` de l'API rejette `ncep_gfs_seamless` (`Data corrupted… Cannot initialize MultiDomains`). `ncep_gfs025` mappe donc vers `gfs_global` (le GFS Global 0,25° affiché sur la carte, cohérent avec le reste de la table qui vise toujours le modèle spécifique, jamais un `_seamless`).

**Variables empruntées à un modèle source (`BORROW_SOURCE_MODELS` + `BORROWED_VARIABLES`, `api.ts`).** Certains modèles ne diffusent pas toutes les variables — l'API les renvoie 100 % `null` (ce n'est PAS une limite d'exposition). Aujourd'hui : **AROME France HD** (`meteofrance_arome_france_hd`, 0,01°) n'a ni `weather_code` (rangée de symboles soleil/nuage) ni `pressure_msl` (axe de pression). `fetchMeteogram()` fait alors une **2ᵉ requête légère** (les `BORROWED_VARIABLES` seules, `buildBorrowUrl`) sur le modèle source `meteofrance_arome_france` (2,5 km, même modèle physique/emprise/run horaire → axes temps identiques, vérifié) et complète par `mergeBorrowedSeries()` **aligné sur le timestamp** (robuste à un décalage ; **base prioritaire** — une valeur déjà présente côté HD n'est jamais écrasée ; `is_day` intact). Échec silencieux (un meteogram incomplet vaut mieux que rien) sauf `AbortError` qui reste propagé. Le vrai correctif reste amont (ajouter ces variables au flux HD). En dernier recours, si `pressure_msl` reste 100 % nulle après emprunt, `buildChartOptions` (`meteogram-chart.ts`) **masque l'axe pression et sa série** (`visible: hasPressure`) pour ne pas laisser un titre « hPa » orphelin sans graduations.

**Le meteogram affiche toujours le dernier run disponible côté API**, pas le run actuellement sélectionné sur la carte (l'API publique ne permet pas de cibler un run passé par ce endpoint) — le tiroir l'étiquette explicitement « dernier run » (`point-drawer.svelte`) pour éviter toute confusion avec le run affiché en carte, qui peut différer.

**Couplage temporel bidirectionnel**, sans re-fetch de la série au scrubbing :

- _Carte → meteogram_ : le playhead est une `plotLine` X du chart Highcharts (id fixe), repositionnée (`removePlotLine`/`addPlotLine`) à chaque changement du store `time` — bouger le scrubber de la carte ne déclenche jamais un nouveau `fetch` ni un re-render du chart, seule la position du trait change.
- _Meteogram → carte_ : un clic sur le chart capture l'échéance sous le curseur, la fait « claquer » sur l'échéance valide la plus proche du run affiché (`nearestValidTime()`, `src/lib/meteogram/snap.ts`, contre `$metaJson.valid_times`) puis appelle `goToValidTime()` — nécessaire car les pas horaires de l'API publique (toutes les heures) ne coïncident pas forcément avec les `valid_times` du modèle affiché (échéances 3-horaires, etc.).
- `src/lib/time-navigation.ts → goToValidTime(date)` est la fonction **partagée** (store `time` + `updateUrl('time', …)` + `changeOMfileURL()`, sans recalage de run) extraite de `playbackAdvance` dans `time-selector.svelte` : la lecture (bouton play) et le meteogram empruntent désormais le même chemin de navigation temporelle. `time-selector.svelte` continue d'appeler `centerDateButton()` par-dessus (spécifique à la barre de dates), que `goToValidTime` ne fait pas.

Rendu **Highcharts** (import dynamique au premier affichage) : `src/lib/meteogram/meteogram-chart.ts` (builder pur `buildChartOptions(MeteogramData): Highcharts.Options`) construit le graphe unique adapté au tiroir sombre (**4 axes Y** : T°+point de rosée / précip / pression / **humidité** ; windbarbs 1/2 ; zoom X ; tooltip partagé ; **légende activée** ; thème sombre). Modules purs data : `src/lib/meteogram/api.ts` (client, `getForecastApiUrl()`), `model-map.ts`, `snap.ts`, `types.ts`, `weather-symbols.ts` — `paths.ts`/`scales.ts` supprimés (rendu Highcharts). Mémoïsation de session dans `meteogram.svelte` (`SvelteMap` clé `lat.toFixed(3),lng.toFixed(3),model` — un changement de modèle force le refetch même à point identique), perdue au rechargement (MVP, comme le sondage).

**Améliorations « retour lecteur » (2026-07-14, spec `docs/superpowers/specs/2026-07-14-meteogram-feedback-lecteur-design.md`).**

- **Légende explicite** (`legend.enabled`, thème sombre) identifiant chaque courbe — corrige la confusion des couleurs.
- **Humidité relative** (`relative_humidity_2m`, ajoutée à `HOURLY_VARIABLES`/`MeteogramKey`) : série violette sur un **4ᵉ axe Y** 0-100 % à droite. **Masquée par défaut** (`visible: false`) mais **présente dans la légende** (`showInLegend` si donnée) → activable d'un clic ; l'axe % porte `showEmpty: false` donc il **n'apparaît qu'une fois la série affichée** (graphe aéré par défaut). Pas d'emprunt pour un modèle qui ne diffuse pas l'humidité (courbe à trous, accepté).
- **Axe temps fusionné** : un **seul** axe X (l'ancien 2ᵉ axe « opposite » des dates est supprimé). Heures (`%H`) par défaut, **date en gras à minuit local** (`labels.formatter` via `chart.time.dateFormat`), séparateurs de jour en `plotLines` calculées par l'export pur **`dayBoundaryPlotLines(times, timezone)`** (repère les minuits locaux via `Intl`, premier point exclu ; edge case fuseaux non-entiers accepté, cohérent avec la limite DST).
- **Vent au tooltip à l'unité de préférence** : `MeteogramChartInput.windDisplay?: { factor; unit }` (défaut km/h) — la valeur du windbarb reste en m/s, seule l'unité d'affichage du tooltip suit `unitPreferences`. **Pas de nombres permanents sur les barbules** : les `dataLabels` windbarb s'ancrent en haut du tracé (pas sur les barbes) → mécanisme écarté (vérifié headless).
- **Réglages fins** : étiquettes de précip 10px, échelle de T° auto-adaptable (pas de `tickInterval` forcé, `minRange: 8` conservé).

Le composant `meteogram.svelte` alimente `humidity` (via `seriesValues`) et `windDisplay` (via `convertValue`/`getDisplayUnit`) dans l'input, **construits synchrones** avant tout `await` (réactivité aux changements d'unité). Il expose aussi une prop bindable **`elevation`** (altitude du point selon le modèle, depuis `elevation` de l'API — `MeteogramData.elevation`) que le tiroir affiche dans son en-tête. Ouverture rapide : **clic droit** sur la carte (`popup.ts → contextmenu`) épingle directement la bulle-viseur compacte (le bouton Météogramme devient cliquable en 1 geste) — la bulle n'est **pas** enrichie (coords/altitude retirées : chargé, et l'altitude terrain n'est pas fiable sans DEM) ; l'altitude vit dans l'en-tête du tiroir. Cf. `.claude/rules/components.md`.

## infoclimat-om-worker integration

The worker URL (`getOmWorkerUrl()`, read from `VITE_OM_WORKER_URL` at build time or `/runtime-config.js` for Docker runtime templating) backs the basemap tile-proxy (`map-controls.ts`). When the URL is unset, that feature is disabled.
